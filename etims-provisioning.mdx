Provisioning connects a company to KRA eTIMS. It's the **one-time setup** that must happen before that company can register items or create sales.

**For most integrations, provisioning is done in the dashboard — not in code.** That's deliberate: it keeps the KRA/OSCU onboarding hoops out of your application. You (or your customer) enter the KRA details once in the dashboard, and Sync2Books does the rest.

When you connect a company, Sync2Books:

1. Maps your **branch key** to the KRA branch
2. Initializes the **eTIMS device** with KRA
3. Activates the **connection**

This is **synchronous** — when it completes, the company is connected and ready.

## Provision in the dashboard (recommended)

1. Open the company in the dashboard.
2. On the **eTIMS** card, enter the KRA details and click **Provision**.
3. Wait for the status to show **Connected**.

![Company → eTIMS provisioning card (enter KRA PIN, provision)](/images/etims/06-company-provision.png)

That's it — no API call required. The company now has a **branch key** (e.g. `HQ`) you'll use in API calls.

## Where the credentials come from

The values you enter are issued by KRA during that business's OSCU onboarding, not by Sync2Books:

| Field | Meaning | Source |
|-------|---------|--------|
| KRA PIN | The business's KRA PIN | The customer's KRA registration |
| Device serial (`dvcSrlNo`) | OSCU device serial number | KRA OSCU service request / device |
| KRA branch ID (`kraBhfId`) | KRA branch office ID (often `00` for head office) | KRA after OSCU approval |
| Environment | `SANDBOX` while testing, `PRODUCTION` when live | You choose |
| Branch key (`sync2booksBranchKey`) | **Your** branch identifier (e.g. `HQ`) used in all later API calls | You choose |

For the full KRA-side process (certification, Integration Token, device initialization, sandbox vs production), see **[eTIMS as a Third-Party Integrator (OSCU)](/ETIMS_OSCU_INTEGRATION_AS_THIRD_PARTY)**.

## branchKey vs kraBhfId vs branch id — don't mix them up

Provisioning and the branches API surface a few different identifiers for the same branch. Only one of them belongs in operational calls:

- **Branch key** (`sync2booksBranchKey` at provision time, `branchKey` on a branch object; e.g. `HQ`) — the **logical branch key you choose**. This is the only one you pass as `branchId` in catalog sync, sales, and stock API calls.
- **`kraBhfId`** (e.g. `00`) — KRA's internal branch office ID. Set once when the branch is created; you do **not** use it in operational API calls.
- **Branch id** (a UUID, called `branchId`/`defaultBranchId` in the provision response, `id` on a branch object) — the platform's internal primary key for the branch row. You use this UUID only as the `:branchId` path parameter on the [branch-management endpoints](/etims-branches) (get/update/initialize/delete a specific branch) — **never** as the `branchId` in catalog/sales/stock calls, where it will 404.

If a catalog/sales/stock call fails with "branch not found," check you passed the **branch key**, not the branch UUID.

## Check provisioning status

You can see a company's eTIMS status in the dashboard, or fetch it programmatically:

```
GET /applications/{applicationId}/companies/{companyId}/integrations/etims/status
```

```bash
curl -X GET "https://api.sync2books.com/applications/{applicationId}/companies/{companyId}/integrations/etims/status" \
  -H "Authorization: Bearer {jwt}" \
  -H "x-application-id: {applicationId}"
```

```json
{
  "status": "connected",
  "connectionId": "7baba7cc-…",
  "details": {
    "complianceTenantId": "9c1e…",
    "complianceBranchId": "b1c2…",
    "environment": "SANDBOX",
    "branchCount": 2
  },
  "branches": [
    { "id": "3fa1e2b0-…", "branchKey": "HQ", "kraBhfId": "00", "isDefault": true, "status": "connected", "...": "see Branches" }
  ]
}
```

`status` and `connectionId` reflect the **Headquarters** branch (the primary connection). `branches` lists every branch on the company — see [Branches](/etims-branches) for the full object shape. `status` is `none` (with an empty `branches` array) when the company has never been provisioned.

This endpoint is JWT-authenticated and requires an `x-application-id` header matching the `:applicationId` in the path — see [Authentication](/concepts/authentication).

## Advanced: provision via API

If you're onboarding **many companies programmatically** (e.g. a bulk migration, or your own onboarding wizard), there's an API-key endpoint that does exactly what the dashboard does. Most integrations won't need this.

```bash
curl -X POST "https://api.sync2books.com/companies/{companyId}/integrations/etims/provision" \
  -H "X-API-Key: {apiKey}" \
  -H "Content-Type: application/json" \
  -d '{
    "kraPin": "P000000045T",
    "environment": "SANDBOX",
    "dvcSrlNo": "DVC-ABC123",
    "displayName": "Mama Mboga Stores",
    "sync2booksBranchKey": "HQ",
    "kraBhfId": "00"
  }'
```

### Request body

| Field | Type | Required | Notes |
|-------|------|----------|-------|
| `kraPin` | string | ✅ | min length 3 |
| `environment` | `SANDBOX` \| `PRODUCTION` | ✅ | |
| `dvcSrlNo` | string | ✅ | OSCU device serial |
| `displayName` | string | — | merchant display name |
| `sync2booksBranchKey` | string | — | your branch key; defaults to head office. **Use this same value** as `branchId` everywhere else |
| `kraBhfId` | string | — | KRA branch office ID, e.g. `00` |

### Response

```json
{
  "connectionId": "7baba7cc-4ae0-48fd-a617-98d55a6fc008",
  "complianceTenantId": "9c1ef2a0-...",
  "defaultBranchId": "b1c2d3e4-...",
  "branchId": "3fa1e2b0-...",
  "environment": "SANDBOX",
  "initialized": true
}
```

| Field | Meaning |
|-------|---------|
| `connectionId` | The platform connection id for the Headquarters branch |
| `complianceTenantId` | Internal compliance-service tenant id — informational |
| `defaultBranchId` | The Headquarters branch's id on the **compliance service** side — informational, not something you pass elsewhere |
| `branchId` | The Headquarters branch's **platform** id (UUID) — use this only as `:branchId` on the [branch-management endpoints](/etims-branches), not in catalog/sales/stock calls |
| `initialized` | Whether the eTIMS device was initialized |

<Warning>
None of the id fields in this response are what you pass as `branchId` in catalog, sales, or stock calls — that's the **branch key** you sent as `sync2booksBranchKey` (or, if you didn't set one, it defaults to `kraBhfId`, e.g. `"00"`). See [branchKey vs kraBhfId vs branch id](#branchkey-vs-krabhfid-vs-branch-id-don-t-mix-them-up) above.
</Warning>

## Idempotency & re-provisioning

- Provisioning an **already-connected** company returns **`409 Conflict`** — it does not silently re-initialize.
- Treat provision as a one-time setup per company/branch. To change KRA details, follow your re-onboarding process rather than blindly re-provisioning.

## Common errors

| Symptom | Cause | Fix |
|---------|-------|-----|
| `409 Conflict` | Company already provisioned | Skip provisioning; it's already connected |
| `400` validation error | Missing KRA PIN / environment / device serial | Provide all required fields |
| Downstream init failure | Wrong KRA PIN / device serial / sandbox not approved | Verify the OSCU onboarding for that business (see the integrator guide) |
