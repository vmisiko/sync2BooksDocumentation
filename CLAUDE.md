# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

This is the public Sync2Books documentation site, built with Mintlify (`docs.json`, `theme: mint`). It's content-only — no `package.json` or build tooling is checked in. To preview locally: `npm i -g mintlify` then `mintlify dev` from this directory.

## Structure

Sync2Books is **two separate products** behind one dashboard: the **Accounting API** (write expenses/bills/invoices/payments to QuickBooks Online, Xero, Sage, Dynamics 365 BC, Odoo) and the **Compliance API** (KRA eTIMS tax compliance for Kenya). Keeping these visibly separate — in navigation, in the reference, in prose — is a deliberate, load-bearing decision; don't quietly re-merge them. `which-api.mdx` is the page that states the split explicitly and is linked from the homepage.

Navigation is defined in `docs.json` with two top-level tabs:
- **Guides** (narrative docs): Get started (`index`, `quickstart`, `which-api`) → Core concepts (`concepts/`: shared by both products — authentication, companies-and-connections, sync-model, environments, errors-and-rate-limits) → **Accounting API — Expenses** (7 pages) → **Accounting API — Connected systems** (`integrations/quickbooks-online/`, `integrations/odoo/`) → **Compliance API — eTIMS (Kenya)** (5 pages, including `ETIMS_OSCU_INTEGRATION_AS_THIRD_PARTY.mdx`) → **Compliance API — Reference (Kenya)** (2 pages) → Link component.
- **Accounting API** (reference): `api-reference.mdx` as a short landing/overview page, then an `Endpoints` group whose pages are auto-generated by Mintlify from `openapi/accounting.json`.

**There is no Compliance API *endpoint* reference tab, and this is deliberate (2026-09-21).** Every
eTIMS endpoint the site used to document lived on the main API under
`/companies/{companyId}/integrations/etims/…`; those routes were removed, because eTIMS is integrated
through the compliance platform and its own API keys, not through the main API. The endpoint pages
(`etims-getting-started`, `etims-provisioning`, `etims-branches`, `etims-catalog`, `etims-sales`,
`etims-stock`, `etims-tracking-results`, `etims-postman`, `etims-api-reference`), `openapi/etims.json`
and the Postman collection were deleted rather than left describing dead routes — recover them from
git history when the replacement `/v1` surface is ready to document. `etims-overview.mdx` is the
single entry point in the meantime, and it says plainly that the developer API is being finalised.

**`Compliance API — Reference (Kenya)` (added 2026-09-28) is data-model reference, not endpoint
docs, and doesn't contradict the above.** `etims-item-attributes.mdx` documents the catalog item
fields (`externalId`, `taxCategory`, `classificationCode`, …) and `etims-item-classification-codes.mdx`
is the KRA `itemClsCd` lookup table (1000 rows, mirrors the values KRA's own OSCU `/selectItemClsList`
returns — pattern similar to what third-party integrators like DigiTax publish). Both pages say only
that the developer API for items is "being finalised" and that a direct `GET`/`POST` surface is not yet
generally available; they name no branches or services. The `/v1` surface itself (P1/P2 of
`sync2books-compliance-api/.docs/COMPLIANCE_SELF_SERVE_API_PLATFORM_PLAN.md`, verified against the KRA
sandbox 2026-09-21) merged to `main` on 2026-09-30. Don't strengthen the "being finalised" wording to
imply a public endpoint exists until the owner confirms `/v1` is open to external developers.

**Don't document the compliance dashboard's own session-authenticated routes here, or in
`sync2books-compliance-api/.docs/TIS_TECHNOLOGY_ARCHITECTURE_V2.md`.** They are internal; publishing
them widens the attack surface around taxpayers' KRA device credentials without helping any
integrator. The public eTIMS surface is the API-key one.

Group titles in the Guides tab are intentionally prefixed (`Accounting API — …` / `Compliance API — …`) so the product split reads correctly even from the sidebar alone, not just from the tab bar.

## The OpenAPI specs (`openapi/`)

`openapi/accounting.json` is **hand-authored**, not generated from the live service — `nest-sync-2-books-api` requires a MySQL connection to boot, and its Swagger doc mixes tags across products. It is the only spec here now; `openapi/etims.json` was deleted with the routes it described (see above). When the underlying API changes:

1. Re-check the relevant controllers under `nest-sync-2-books-api/src/` — `company`, `connection`, `expense`, `bill`, `invoice`, `bill-payment`, `attachment`, `sync`. `src/compliance/` no longer exposes public routes; what remains there is the inbound callback from the compliance service.
2. Update the matching path/schema in `openapi/accounting.json` by hand.
3. Validate with `npx @redocly/cli lint openapi/accounting.json` before committing (expect some pre-existing warnings about missing `operationId`/4xx responses — not required by Mintlify; don't chase those to zero).

Known, deliberately-not-hidden quirks baked into `openapi/accounting.json` (confirmed against source, not spec bugs):
- `POST /bills/{connectionId}` vs `PUT /bills/{id}` (and the equivalent pairs for expenses, invoices, and bill payments) are structurally identical route shapes with different param names — Redocly's `no-identical-paths` rule flags this as 4 errors; it reflects the real deployed routes, not an authoring mistake.
- The Connection resource's low-level CRUD (`POST /connections`, `GET/DELETE /connections/:id`, `PUT /connections/:id/refresh-token`) is deliberately **not** included in the public Accounting API reference — it's internal plumbing (raw OAuth token ingestion during the Link/OAuth callback flow), not something a third-party integrator calls directly. Only the genuinely-public Connection routes (`GET .../company/:companyId`, `.../integration/:integrationKey`, `POST .../disconnect`) are documented, matching what the guides actually tell developers to call. These previously had no auth guard at all (a real gap, not an intentional design) — that's been fixed at the API layer (`ApiKeyAuthGuard` + `RateLimitGuard` added to every one of them); the reference still excludes them on scope grounds, not auth grounds.

### Resolved (2026-08-27)

Two bugs surfaced while building this reference and were fixed at the API layer, not just documented around:
- `GET /bills`, `PUT /bills/{id}` in `nest-sync-2-books-api` read `req.user.applicationId`, but the guard on that controller (`ApiKeyAuthGuard`) sets `req.application`, never `req.user` — every call threw. Fixed to use `@ApplicationContext()` like every sibling handler.
- `BillPaymentController` (`bill-payment.controller.ts`) was gated by `JwtAuthGuard` and read `connectionId`/`companyId`/`applicationId` off `req.user` — but the dashboard JWT payload (`jwt.strategy.ts`) only ever carries `userId`/`email`/`role`/`organizationId`, so those three fields were always `undefined`. The endpoint could not have worked for any caller. Switched to `ApiKeyAuthGuard` + `@ApplicationContext()` + a `:connectionId` route param, matching Bill/Invoice/Expense — `POST /bill-payments` is now `POST /bill-payments/{connectionId}`. `BillPaymentService.createBillPayment`'s `companyId` param is now optional and derived from the connection when omitted, so the one existing internal caller (`bill.service.ts`'s `createBillWithPayment`, which already supplied it) is unaffected.

`assets/sync2books-TIS-Technology-Architecture-v2.pdf` is **generated**, not hand-edited: the markdown
source lives at `sync2books-compliance-api/.docs/TIS_TECHNOLOGY_ARCHITECTURE_V2.md` and the PDF is
rebuilt with `python3 scripts/build-architecture-pdf.py`. Edit the markdown and rebuild, or the two
drift apart. `etims-architecture.mdx` is the page that links it; update its page count when the
document grows.

When editing, match the existing `.mdx` structure/frontmatter of neighboring pages in the same section rather than introducing a new format.
