# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

This is the public Sync2Books documentation site, built with Mintlify (`docs.json`, `theme: mint`). It's content-only — no `package.json` or build tooling is checked in. To preview locally: `npm i -g mintlify` then `mintlify dev` from this directory.

## Structure

Sync2Books is **two separate products**: the **Accounting API** (write expenses/bills/invoices/payments to QuickBooks Online, Xero, Sage, Dynamics 365 BC, Odoo) and the **Compliance API** (KRA eTIMS tax compliance for Kenya). Keeping these visibly separate — in navigation, in the reference, in prose — is a deliberate, load-bearing decision; don't quietly re-merge them. `which-api.mdx` is the page that states the split explicitly and is linked from the homepage.

Navigation is defined in `docs.json` with three top-level tabs:
- **Guides** (narrative docs): Get started (`index`, `quickstart`, `which-api`) → Core concepts (`concepts/`: Accounting API concepts — authentication, companies-and-connections, sync-model, environments, errors-and-rate-limits) → **Accounting API — Expenses** (7 pages) → **Accounting API — Connected systems** (`integrations/quickbooks-online/`, `integrations/odoo/`) → Link component.
- **Accounting API** (reference): `api-reference.mdx` as a short landing/overview page, then an `Endpoints` group whose pages are auto-generated by Mintlify from `openapi/accounting.json`.
- **eTIMS API** (the Compliance API's own tab, added 2026-10): Start here (`etims-overview`, `etims-quickstart`, `etims-authentication`, `etims-concepts`) → Guides (`etims-guide-items|sales|credit-notes|stock|purchases`, `etims-callbacks`) → API conventions (`etims-idempotency`, `etims-errors`, `etims-pagination`, `etims-rate-limits`) → Reference data (`etims-codes`, `etims-item-attributes`, `etims-item-classification-codes`) → Going live (`etims-going-live`, `ETIMS_OSCU_INTEGRATION_AS_THIRD_PARTY`, `etims-architecture`) → API reference (`etims-api-reference`) → an `Endpoints` group whose pages Mintlify generates from `openapi/etims.json` → `etims-changelog`.

**eTIMS lives in its own tab (re-homed 2026-10).** On 2026-09-21 the eTIMS endpoints were removed from
the main API's section of this site, because eTIMS is no longer integrated through the main API: the
Compliance API handles its own integration directly, with its own API keys. That removal was about
where eTIMS is documented, not a decision to withhold it. The **eTIMS API** tab now documents the
Compliance API's `/v1` surface, and its endpoint pages are generated from `openapi/etims.json`. The
Accounting side points to it from `which-api`, the homepage and the Accounting API overview. Do not
document eTIMS endpoints in the Accounting tab or in `openapi/accounting.json`.

The **Reference data** group (`etims-codes`, `etims-item-attributes`, `etims-item-classification-codes`)
documents the fields and codes the `/v1` endpoints take. `etims-item-classification-codes` is a
snapshot of the 1000-row KRA `itemClsCd` table; the live `GET /v1/lookups/classifications` is
authoritative and the page says so.

**The Compliance API base URL lives in three places that change together:** `snippets/etims-base-url.mdx`
(the source for prose, imported with `import { baseUrl } from "/snippets/etims-base-url.mdx"`), the one
`export S2B_URL=...` line in `etims-quickstart` (code blocks cannot interpolate a snippet, so every other
curl sample uses `$S2B_URL`), and `servers` in `openapi/etims.json`. Sandbox
and production share the one host; the key (`cmp_sk_test_…` or `cmp_sk_live_…`) and the business it
acts on decide which KRA environment is reached.

**Don't document the compliance dashboard's own session-authenticated routes here, or in
`sync2books-compliance-api/.docs/TIS_TECHNOLOGY_ARCHITECTURE_V2.md`.** They are internal; publishing
them widens the attack surface around taxpayers' KRA device credentials without helping any
integrator. The public eTIMS surface is the API-key one. Result callbacks are documented as **unsigned** (no
HMAC, no secret) until payload signing ships; change `etims-callbacks` when it does.

Group titles in the Guides tab are prefixed `Accounting API — …` so the product split reads correctly even from the sidebar alone. Inside the eTIMS API tab the prefix is dropped, because the tab name carries it.

## The OpenAPI specs (`openapi/`)

There are two specs, both **hand-authored**, not generated from the live services. `openapi/accounting.json` describes the Accounting API: `nest-sync-2-books-api` requires a MySQL connection to boot, and its Swagger doc mixes tags across products. `openapi/etims.json` describes the Compliance API's `/v1` surface (24 operations plus the result callback as a `webhooks` entry).

**`openapi/etims.json`** is sourced from `sync2books-compliance-api/src/developer-platform/presentation/v1/` (the controllers, `v1-input.ts` for request limits and enums, `v1-views.ts` for response shapes, `v1-error.filter.ts` for error codes) and the guards under `infrastructure/guards/` for auth, scopes and rate limits. Never copy the service's own Swagger or `.docs/openapi.json`: they are internal and stale. Validate with `npx @redocly/cli lint openapi/etims.json` (expect only the `info-license` warning). Any `/v1` change must update this spec, the matching guide page and `etims-changelog`. Keep examples obviously fake (PIN `P000000000X`, ids like `itm_example_1`, key `cmp_sk_test_xxxxxxxxxxxxxxxxxxxxxxxx`), and never describe internal topology in it.

**`openapi/accounting.json`** is maintained as follows.

1. Re-check the relevant controllers under `nest-sync-2-books-api/src/` — `company`, `connection`, `expense`, `bill`, `invoice`, `bill-payment`, `attachment`, `sync`. `src/compliance/` no longer exposes public routes; what remains there is the inbound callback from the compliance service.
2. Update the matching path/schema in `openapi/accounting.json` by hand.
3. Validate with `npx @redocly/cli lint openapi/accounting.json` before committing (expect some pre-existing warnings about missing `operationId`/4xx responses — not required by Mintlify; don't chase those to zero).

Known, deliberately-not-hidden quirks baked into `openapi/accounting.json` (confirmed against source, not spec bugs):
- `POST /bills/{connectionId}` vs `PUT /bills/{id}` (and the equivalent pairs for expenses, invoices, and bill payments) are structurally identical route shapes with different param names — Redocly's `no-identical-paths` rule flags this as 4 errors; it reflects the real deployed routes, not an authoring mistake.
- The Connection resource's low-level CRUD (`POST /connections`, `GET/DELETE /connections/:id`, `PUT /connections/:id/refresh-token`) is deliberately **not** included in the public Accounting API reference — it's internal plumbing (raw OAuth token ingestion during the Link/OAuth callback flow), not something a third-party integrator calls directly. Only the genuinely-public Connection routes (`GET .../company/:companyId`, `.../integration/:integrationKey`, `POST .../disconnect`) are documented, matching what the guides actually tell developers to call. These previously had no auth guard at all (a real gap, not an intentional design) — that's been fixed at the API layer (`ApiKeyAuthGuard` + `RateLimitGuard` added to every one of them); the reference still excludes them on scope grounds, not auth grounds.

### Resolved (2026-08-27)

Two bugs surfaced while building this reference and were fixed at the API layer, not just documented around:
- `GET /bills`, `PUT /bills/{id}` in `nest-sync-2-books-api` read `req.user.applicationId`, but the guard on that controller (`ApiKeyAuthGuard`) sets `req.application`, never `req.user` — every call threw. Fixed to use `@ApplicationContext()` like every sibling handler.
- `BillPaymentController` (`bill-payment.controller.ts`) was gated by `JwtAuthGuard` and read `connectionId`/`companyId`/`applicationId` off `req.user` — but the dashboard JWT payload (`jwt.strategy.ts`) only ever carries `userId`/`email`/`role`/`organizationId`, so those three fields were always `undefined`. The endpoint could not have worked for any caller. Switched to `ApiKeyAuthGuard` + `@ApplicationContext()` + a `:connectionId` route param, matching Bill/Invoice/Expense — `POST /bill-payments` is now `POST /bill-payments/{connectionId}`. `BillPaymentService.createBillPayment`'s `companyId` param is now optional and derived from the connection when omitted, so the one existing internal caller (`bill.service.ts`'s `createBillWithPayment`, which already supplied it) is unaffected.

`assets/sync2books-TIS-Technology-Architecture-v2.pdf` is **generated**, not hand-edited: the markdown
source lives at `sync2books-compliance-api/.docs/TIS_TECHNOLOGY_ARCHITECTURE_V2.md` and the PDF is
rebuilt with `python3 scripts/build-architecture-pdf.py`. Edit the markdown and rebuild, or the two
drift apart. `etims-architecture.mdx` is the page that links it; update its page count when the
document grows.

When editing, match the existing `.mdx` structure/frontmatter of neighboring pages in the same section rather than introducing a new format.
